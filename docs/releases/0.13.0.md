# 0.13.0

Phase 4: today's fault, best scores kept in the browser, Share, and a loading screen.

## Added

- A start screen with "Today's fault · Day N" and "Free play". Today's fault is the same for everyone, with the same customer, chosen from the day number in Lagos time (plan 0014, ADRs 0005, 0015). 2026-10-11 is Day 10.
- The first attempt each day is scored. It is used up when its timer starts: a daily left mid-round (a closed tab, a reload) counts, and the start screen shows it as "Not finished" (plan 0014, ADR 0024). After that the button reads "Today's fault · practice"; practice rounds say "Not scored" and are not saved.
- The result screen shows your best score for the fault and "New best" when you beat it. Only fixed rounds count; a walk-out is never a best (ADRs 0001, 0022).
- Scores are saved under one browser key, `openam.scores.v1`, in the shape ADR 0022 sets. When storage is blocked, full or broken, the game keeps this session's results in memory and plays on (ADR 0005).
- A scored daily that ends with the engine running can be shared as ADR 0005's three lines, for example `Open Am · Day 12` / `Fixed in 38s · 1 wrong part · ★★★` / the link. It goes through the phone's share sheet, otherwise the clipboard ("Copied"), otherwise the text is shown to copy by hand. The link is the page's address with no query, so `?diag` never leaks (plan 0014, ADR 0005).
- A wordless pulsing bar shows before any script runs. The start screen and briefing then show as soon as the small data files arrive, and the model, ground shadow, environment and hand load behind them. The briefing shows a progress bar and keeps "Start" disabled until the machine is in (plan 0014, ADR 0014).
- A development-only `?today=<ISO time>` query sets the date, to see a day change in the browser.
- 295 tests, up from 246: the daily provider across Lagos midnight; the daily's fault and customer, the attempt used at the timer's start, a daily ended after midnight kept on its day, walked and unfinished dailies, practice not saved, free play saved with no day, the saved score equal to the log's score; the store (lowest total, walk-outs, unfinished records, a reload, storage that throws, a quota error, unreadable JSON); every share route; the exact ADR 0005 text; the start screen's text; loading progress.

## Changed

- "Next customer" returns to the start screen, so free play takes one more tap ("Free play") per round (plan 0014 reading 1).
- `npm run verify:phone` taps "Free play" before each round and fails when the frame rate at 4x CPU throttle is under 30 fps, or cannot be read (`FPS_BUDGET`, ADR 0014). It now also checks: the loading bar with "Start" disabled while the model is held back on a throttled network; a scored daily that names the day, shows the best and Share, and copies the exact ADR 0005 text; the daily reading practice after a reload, with a practice result that is not scored; a daily left mid-round reading "Not finished" (ADR 0024); the next day offering a new daily; a round with `localStorage` throwing, with no console errors. `OPEN_AM_FPS_BUDGET` overrides the budget, to show the failure.
- `npm run verify:drop` taps "Free play" and waits for "Start" to be enabled.

## Fixed

- The browser checks left a headless Edge running on their debug port after each run (on Windows the launched `msedge.exe` hands over to another process, so killing its pid missed it). The next run on that port reused it, with the previous run's saved scores. Both checks now close the browser over DevTools, and the phone check clears the game's `localStorage` before it starts.

## Checked

- `npm test` (295), `npm run typecheck`, `npm run docs:check`, `npm run build`, `npm run size` (184.3 KB gzipped of 350 KB). `game/tests/boundaries.test.ts` unchanged and passing.
- `npm run verify:phone`, exit 0: 6 of 6 faults, forced walk-out ok, every loading and daily check above, storage blocked ok, hand at most 9% hidden (limit 10%), 117 fps at 4x CPU throttle against the 30 fps budget, 0 console errors. The shared text was `Open Am · Day 20` / `Fixed in 10s · 0 wrong parts · ★★★` / `http://localhost:5197/`.
- With `OPEN_AM_FPS_BUDGET=1000` the run exits 1 with "frame rate: 116 fps at 4x CPU throttle is under the 1000 fps budget (ADR 0014)". That run also failed its daily checks, which led to the fix above.
- `npm run verify:drop`, exit 0: 96 of 96 removals first time, machine never under the controls, frame rate held, 0 console errors. One earlier run reported "Frame rate: FELL as parts came off" with every removal first time (per-round readings between 49 and 120 fps while other agents ran Blender and browser checks on this machine); the next two runs held. Headless software rendering under CPU contention is noisy.

## Known gaps

- Waiting on the owner, on a phone over mobile data: the start screen showing within a moment, the progress bar on the briefing, the daily scored and then practice, and Share opening the phone's share sheet. The headless check has no share sheet, so only the clipboard route is checked in a browser; the sheet route is covered by unit tests.
- When the phone has a share sheet, a cancel and the rare case of a broken sheet with a refused clipboard both come back as "none" (the `Share` interface has no separate cancel). Both do nothing more; the player can tap Share again. The hand-copy box shows only when there is no sheet and the clipboard refuses.
- The frame rate was measured only in headless Edge with software rendering. Passing it is necessary, not sufficient, for a low-end phone.
- Plans 0011 (`tools.glb`) and 0012 (`toolbox.glb`) will add their files to the loading progress when they merge; whichever merges second rebases `main.ts`, `ui/index.ts` and `tools/verify/phone-play.ts`.
- The phone preview was not republished from this branch: it is not merged.
